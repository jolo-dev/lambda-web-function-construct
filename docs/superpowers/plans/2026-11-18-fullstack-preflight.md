## Findings and recommendation

### Lambda Web Function OAC, dynamic cache policy, and CDK support

The official [CloudFront OAC guide for Lambda Web Function origins](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-lambda-web.html) explicitly requires `Authorization` in the cache policy when the Web Function uses the viewer's Authorization header. It explains that CloudFront does not forward this header unless it is in the cache policy. The separate [Lambda Web Function endpoint access-control guide](https://docs.aws.amazon.com/lambda/latest/dg/web-functions-endpoint-access-control.html) describes CloudFront OAC signing for IamAuth endpoints and that application Authorization can be passed through to the function while CloudFront signs its origin request. Follow the Web-Function-specific docs; do not substitute the ordinary Function URL OAC contract.

**Candidate, not yet service-validated:** use a custom `AWS::CloudFront::CachePolicy` with minimum, default, and maximum TTL all `0`, `Authorization` in the allowed cache-key header list, and no cookie/query-string cache-key values; pair it with `OriginRequestPolicy.ALL_VIEWER_EXCEPT_HOST_HEADER`. The custom cache policy places Authorization in the key as AWS requires; zero TTLs disable shared reuse. The origin request policy forwards viewer cookies, query strings, and other viewer headers, except viewer `Host`. This is preferable to managed `CachingDisabled`, whose cache-key headers do not meet the documented Authorization requirement. Treat possible AWS control-plane policy validation as unresolved until an explicitly approved live test; synthesis is not service acceptance evidence.

Locally synthesized this candidate with installed `aws-cdk-lib` **2.274.0**, setting `SigningBehavior.ALWAYS_AMZ_AUTH` and `SigningProtocol.SIGV4`. The emitted CloudFormation had `MinTTL`, `DefaultTTL`, `MaxTTL` all `0`; `HeadersConfig.HeaderBehavior: whitelist` and `Headers: [Authorization]`; zero cookies and query strings in the cache key; the `AllViewerExceptHostHeader` managed-policy ID (`b689b0a8-53d0-40ab-baf2-68738e2966ac`); and OAC config `OriginAccessControlOriginType: lambda`, `SigningBehavior: always-amz-auth`, and `SigningProtocol: sigv4`. The distribution origin references the OAC ID. This proves CDK can express and synthesize the candidate only. It does not establish that CloudFront accepts or behaves as intended for every method.

**CDK OAC declaration findings:** the installed declarations are from `aws-cdk-lib` 2.274.0 (`package.json` pins that dev dependency; construct peer range is `^2.274.0`). `aws-cloudfront/lib/origin-access-control.d.ts` offers L2 OACs for S3, Lambda Function URLs, and MediaPackage V2, but no Lambda Web Function-specific L2 class. It does define `SigningBehavior.ALWAYS_AMZ_AUTH` (`"always-amz-auth"`) and `Signing.SIGV4_ALWAYS_AMZ_AUTH`; the generated L1 `CfnOriginAccessControl` accepts a string for `signingBehavior`, so pass `SigningBehavior.ALWAYS_AMZ_AUTH` with origin type `"lambda"` and signing protocol `"sigv4"`. **Do not use `SigningBehavior.ALWAYS` (`"always"`)**: AWS requires `always-amz-auth` for Lambda Web Function OAC, which signs through its dedicated header while preserving viewer Authorization. `HttpOrigin` **can bind** the resulting Lambda OAC ID: `HttpOriginProps` extends `cloudfront.OriginProps`, which exposes `originAccessControlId?: string`; the synthesized distribution origin includes the OAC ID. Supported route is therefore `CfnOriginAccessControl` plus `new HttpOrigin(hostname, { originAccessControlId: oac.attrId })`, not a custom resource and not the Function URL OAC L2. `Distribution` behavior accepts the cache policy and origin request policy directly. Declaration files inspected: `aws-cloudfront/lib/cache-policy.d.ts`, `origin-access-control.d.ts`, `origin.d.ts`, `distribution.d.ts`, and `aws-cloudfront-origins/lib/http-origin.d.ts`.

## Candidate verification matrix for implementation and service acceptance

These are required evidence cases for the dynamic behavior, not tests run in this task:

1. **GET + Authorization:** send `GET` with `Authorization: Bearer <token-A>` and then `Authorization: Bearer <token-B>`. Verify dynamic code receives each exact viewer header and returns the corresponding token-specific result; neither request may receive a response shared with the other token.
2. **POST + Authorization:** send the mutation `POST` with `Authorization: Bearer <token-A>` and then repeat with `Authorization: Bearer <token-B>` (same path/body, where suitable). Verify dynamic code receives each exact viewer header and returns the corresponding token-specific mutation result; neither response may be shared across tokens. Verify the method/body are preserved while CloudFront OAC signs origin access with `always-amz-auth`.
3. **Cookies:** distinct cookie values reach dynamic code; prove no cached response crosses cookie identities.
4. **Query strings:** query values reach dynamic code and distinct values are evaluated independently.
5. **Errors:** origin 4xx/5xx responses and malformed/unauthorized requests are not masked by SPA rewrites or incorrectly reused; record status, body behavior, and cache headers.
6. **Host/proxy context:** `Host` is the endpoint origin host rather than viewer Host; viewer-request transformation overwrites `X-Forwarded-Host` with actual viewer host and `X-Forwarded-Proto` with HTTPS.
7. **Static vs dynamic:** explicit immutable S3 paths remain cacheable; dynamic paths have no shared response reuse, including when origin responses provide cache headers.

**Policy acceptance criteria before declaring deployable:** (a) CloudFront accepts the custom cache policy with Authorization and all three TTLs zero; (b) synthesized/live behavior forwards Authorization on both GET and POST without exposing the viewer Host; (c) cookies/query strings and required framework headers arrive at origin; (d) dynamic requests with differing authorization/cookie/query identities do not reuse a response; (e) policy validation does not require weakening disabled shared caching or removing Authorization. If any condition fails, stop for design review; do not silently switch to application-managed auth or a cache-enabling policy.

**Live test is approval-gated.** Before any AWS action, present account, region, stack/resource list, anticipated cost drivers, limits, bounded request schedule, and exact cleanup commands, then obtain explicit operator approval. The design approval is not deployment approval. Include Authorization GET and POST, cookie/query distinctions, no-cache assertions, errors, static asset controls, and unsigned direct-origin rejection in the bounded live test. No deployment, resource creation, paid probe, AWS API call, or cleanup was performed for this task.
